### 七、诚实边界（逐条）

1. **工单 §二 的三条假设，两条没能站住，一条被精确化**（都以数字为准，不因"工单这么写"而迁就）：① 假设 2「拖拽期间系统忽略我们的 z 序改动」—— **证伪**（§一.②，`ret=True err=0` 且真换位并保持）；② 假设 1「`wp_zw_behind` 之后没验收就上闩」—— **不是**本复现里"面板赖在上面"的直接原因（干净夹具下 trace 整段冻住 = 面板**一次动作都没发**），但把"验收"删掉**照样当场红**（§五 VARIANT 2），它有它自己的承重方式：**没有它，面板下一帧就自己把让位撤销**；③ 假设 4「`wp_fg_above()` 拖拽期间读错」—— **读数没错**：拖拽中窗口 z# 真的在面板之下（37 vs 34），错的是**决策规则**：用户正把窗口拖到面板上时，"你在我下面"不该成为不让位的理由。
2. **能触发的形状很具体：只有"拖一个已经是前台的窗口"才会撞上这个 bug**。拖一个**不是**前台的窗口时，按下那一下会激活并抬高它（实测 z# 40 → 34），面板本来就会让位（Q2(d)）⇒ 日常里表现为"我拖我正在用的那个窗口，面板不让；换一个别的窗口拖，好像又让了"。
3. **"正在拖"的判定是启发式**（左键按住 ＋ **前台窗口矩形**在相邻两帧之间变了），已知漏报：① 短于两个策略帧的拖拽（本机循环实测 ≈60/s ⇒ 约 30 ms 以下）；② **键盘/系统菜单的"移动"**（`Alt+Space` → 移动、方向键）——没有按键按下 ⇒ 不认，此路仍是 M13 的规则（面板不让位）；③ **触摸/笔拖拽**（`in.down` 来自 `GetAsyncKeyState(1)` 左键，未实测）；④ 别的进程**在用户没按键时**程序化移动窗口 —— **刻意不认**（那正是 C11f 要守的场景）。
4. **让位发生在"拖拽进行中"**（实测：动几步之内），**不是**靠松手触发；若整段拖拽都被漏掉（见上条 ①），面板**不会事后补**（没有"事后重判"的机制）—— 工单 §四 那句"松手后的第一个采样能补上"在本机是**由"拖拽中就已经让位"满足的**，不是由松手后的检测满足的，这点如实写。
5. **节拍与开销**：未确认的让位**不会**在 ≈60/s 的循环里每帧重发（`wp_yield_t0` 卡到 2 s 策略节拍）；拖拽中只要"让位未确认"，面板**不会**走 `auto-front`（这正是让位立得住的原因）；本刀**没有任何每帧新增的 API 调用或 z 序走链**（矩形与按键都是已有的本帧读数，走链只发生在状态迁移时）。
6. **`wp_drag_seen` 的生命周期**：前台换人 / 窗口不再与面板相交 / **让位被确认** 三者之一即清；若窗口一直保持前台且一直压在面板上，它会留着（无害：那种状态下 `wp_fg_top` 本身就已经是 1）。已写进源码注释。
7. **C11h 的承重读数是 z 序走链，不是 `WindowFromPoint`**：本机屏幕上第三个窗口经常占着"面板 ∩ 窗口"的重叠中心（三次变体运行里 `WindowFromPoint` 都答了第三个 handle），所以判据只用走链判相对 z 序，`WindowFromPoint` 只打印读数。**C6u/C10e 这两条像素判据在三次变体运行里都红**，与本次改动无关（同一台机器上真人在用、有窗口压在采样区上的历史签名，见 v13 §七.5）；**最终不跳段全套件里两条都绿**，门限一个字未改。
8. **本刀没有新导入**（83/7/96 不变）；`main.fl` 的 globals **只收字面量**（新增 9 个 `int` 全部 `= 0`）；本刀**零新增键盘注入**（套件唯一的键盘注入仍是 M8 的 `C6x4`/`C6x4b`）。面板自己的矩形**任何路径都不会被本刀移动**（前后两次实测都未变）。

### 七、诚实边界（逐条）

1. **平台层的"全局左键轮询"本身没改**（`lib\flgui_win32.fl` 那句 `GetAsyncKeyState(1)` 照旧）：本刀只在 **app 层**把它的产物（全局按下沿）**过滤**成"真的点了我"。改平台层＝改所有 GUI 应用的输入语义，属**单独一刀**，且本刀的判据已经能把这个过滤的两条失败路径都钉住。
2. **不是 `WindowFromPoint`**：该 API 在本工具链里**不可调用**（§三 的实测：api 形参只能 `int`，8 字节按值 POINT 传不出去）。用的是"走链 ＋ 矩形"等价问法 ⇒ **已知边界**：对**分层窗口在光标处像素透明**的情形（或异形窗口），本判定仍会把那个窗口算作"盖住了"（`WindowFromPoint` 会看穿它）。这个方向的误差只会让面板**少认**一次自己的点击，**不会**反过来把别人的点击认成自己的；判据的对照半（面板正中点击必须计数）在真实布局下把守这一点。

### 七、诚实边界（逐条）

1. **前台窗口在面板下面、而用户真想用它**：本刀之后面板**不会**自己让开（这正是本条要的），所以用户只能**点那个窗口露在面板之外的部分**让它被激活、由系统把它抬到面板之上 —— 那时层级条件成立，面板才会让位。**没有任何"猜用户想让谁上来"的机制**。
2. **层级读数的采样延迟**：`wp_fg_top` 与 `wp_zcover` 同一 **2 s** 节奏（只有"切到 auto / 按 Auto 键"那一帧强制重采）。所以"某个窗口刚被抬到面板之上"最多滞后约 2 s 才被采纳（与 v11 已交付的让位/回位延迟同源）。
3. **走链这把尺子本身的边界**：① 上限 256 步（面板在普通带靠前，实测链长 34~37，远未触顶）；② 窗口族用 **pid** 判：若同一个进程**既有**窗口在面板之上、**又有**窗口在面板之下，只要在上的那个可见非最小化，就判定"前台在上" ⇒ 会按 v11 语义给聚焦窗口让位（同族多窗时这仍是用户想要的）；③ 只在**顶层链**上走，不查子窗层级（`GetForegroundWindow` 返回的就是顶层窗口）。
4. **置顶带例外**：面板仍在置顶带时（从 `top` 切 `auto`、或面板刚起来还没离开置顶带），层级条件**不生效** ⇒ 那一帧仍会给聚焦窗口让位。这是**刻意**的（`C11a`/`C6x3` 的语义就是它），已写进 §三 与这段。
5. **v11 那套"用户刚碰过我"的抑制比字面更宽**（本刀实测发现，**未改**）：`gui_win_input()` 轮询**全局**左键 ⇒ **桌面上任何点击**都会被面板当作"点了我"并武装抑制，解除条件是"前台换人"。所以稳态下 `auto` 往往处在抑制态（这也是工单给的 A/B 次序复现不出来的原因之一）。**动它＝改 v11 已交付语义，需要单独一刀与单独判据**，本刀只披露。
6. **"让位"动作本身有搬动能力**（`probe-zw-order` 实测：`SetWindowPos(panel, after=X)` 真换位、`HWND_BOTTOM` 真沉底），所以这不是"反正搬不动"的伪修复。
7. 窗口位置/尺寸仍**不持久化**；`Setup` 与滑条 `opacity` 字样仍英文（老边界，未动）。
8. 本刀**零新增键盘注入**；套件唯一的键盘注入仍是 M8 的 `C6x4`/`C6x4b`（只注入面板自己注册到的组合）。
9. 判据 `C6u` 是**像素尺子**，本机可能因"桌面在两次抓图之间有窗口移动"而红（历史记录里有 `median 17.7` 那次）。本刀两次"能红"轮里它也红过，**与被测改动无关**（同一份代码在**最终不跳段全套件**里 `C6u` 绿）。`C6u` 的两条门限（median ≥ 20 未动 ＋ v11 加的 sum ≥ 1000）本刀**一个字没改**。

### 三、修法（含动手前实测出的 Windows z 序规则）

**先量后写**（`tmp\m10\probe-zw-inspect.ps1`，两个 notepad 做 A/B，每次调用都打返回值与 `GetLastError`）：

| 调用 | 返回 | z 序实测 |
|---|---|---|
| `HWND_TOP=0`（`0x13` 与 `0x3` 两种标志） | True, err=0 | **不动** |
| `BringWindowToTop` | True, err=0 | **不动** |
| `HWND_BOTTOM=1` | True, err=0 | 31 → 164（下沉） |
| `HWND_NOTOPMOST=-2`（窗**非置顶**时） | True, err=0 | **不动** |
| `HWND_TOPMOST=-1` | True, err=0 | 164 → **15**、top=True |
| `HWND_NOTOPMOST=-2`（窗**置顶**时） | True, err=0 | 15 → **28**、top=False（= 普通带最前） |

⇒ **后台进程不能"带内抬升"**（`HWND_TOP`/`BringWindowToTop` 静默成功但不重排）；**只有"带间迁移"（`±1`/`-2`）真能重排**。

## v8 追加刀（2026-10-10）：热键「临时顶 / 锁定顶」—— 按住 = 临时到最前；按住 ＋ `T` = 真顶到最前

> 工单 = `E:\FLINT-lab\工单-面板M8-热键临时顶.md`｜用户原话「**在原有的基础上加一个热键，按住后临时顶到顶层，再加一个键就真顶到顶层**」＋「**还是可能抢键，想一个解决方式**」｜开工前 HEAD = M7 交付后的 `a45b497`
> 本刀 = **纯 `apps\winpanel\` 改动**（`main.fl` ＋ `verify-panel.ps1`）；`lib\` / `src\` / `boot\` / `test\` **一个字节没动**。

### 一、口径（用户原话 → 落法）

- **按住热键** ⇒ 面板**临时**进置顶带；**松开就回原档**（按住那一刻记下 top/normal/auto 及 auto 是否正被盖着，松开**原样还原** —— 原来 auto 被盖着就回"让位"态，**不偷偷变 top**）。
- **按住的同时再按 `T`** ⇒ 把档**锁**在 `top`（= Setup 页 `Layer: top` 的**同一个**状态，不发明第二套）；**再按一次 `T`** ⇒ 解锁、回到按住前那个档。
- **可见反馈**：底栏多了 `hk ^!W`（当前真正生效的热键）／`peek`（正在临时顶）／`top*`（已锁）。

### 二、"抢键"的解法：不抢，**申请独占 ＋ 自动降级 ＋ 看得见**（七条全部实测）

探针 `tmp\m8\hotkey-probe.ps1` 在本机量到（读数 `tmp\m8\hotkey-probe-run.txt`）：

| # | 事实 | 读数 |
|---|---|---|
| 1 | 自己 `RegisterHotKey(Ctrl+Alt+W)` | 成功 |
| 2 | 同一进程重复申请 | **失败 1409** |
| 3 | **另一个进程**申请同一组合 | **失败 1409** ⇒ 独占是真的 |
| 4 | 子进程占着 `Ctrl+Alt+P` 时我们申请 | **失败 1409** ⇒ 冲突**可检测** |
| 5 | **kill 掉占着的子进程**后再申请 | **立刻成功** ⇒ **崩溃不留鬼影** |
| 6 | 注入的按键对 `GetAsyncKeyState` | 按住读 down／松开读 up ⇒ "按住"可判 |

### 四、⚠️ 本刀途中的一次真事故（20:09，必须记）

**事故**：为验证"注入的键能不能被轮询读到"，探针注入了一次**裸的 `Ctrl+W`**（**没有注册给任何人**）⇒ 它**直接打到用户当时的前台窗口**（用户当时只开着浏览器和终端；多数程序里 `Ctrl+W` = 关标签/关窗口）⇒ **用户的应用窗口被关**，两分钟后 DSH web 重启报 3080 被**旧 node** 占用（**与探针无关**：全程只按 PID 杀过 winpanel / notepad / 自己的子进程，从没碰 node）。

**三条硬规则（已写进探针注释 ＋ 工单 ＋ 判据）**：
1. **只注入本进程 `RegisterHotKey` 注册过的组合** —— 注册过的组合被系统吞掉（以 `WM_HOTKEY` 交给注册者），**别的应用根本收不到**；这也正是面板热键本身安全的原因。
2. **绝不在活桌面上注入裸的 `Ctrl`/`Alt` 组合**（不存在"安全的"裸组合）。
3. 判据里**注入前必须先证明面板确实占着那个组合**（脚本自己 `RegisterHotKey` 必须被拒 1409），**证不出来就一个键都不发**（判 FAIL 并写明 REFUSED TO INJECT）。

- **`checks total=96 passed=96 failed=0` → ALL GREEN**（全文 `tmp\m8\verify-run-02.txt`）。

### 六、诚实边界（逐条）

1. **中键备用入口不在判据里**：它的可观察量（置顶位）要求面板此刻**不置顶**，而那时面板矩形上压着别人的窗口，自动化点中键会打到**别人的窗**（浏览器中键 = 自动滚动）⇒ 为了不碰用户的程序，这一条**只做人工验、不写自动判据**（不是漏，是明确不做）。
2. **注册独占挡不住低级键盘钩子**（`WH_KEYBOARD_LL`）：若某程序用钩子监听同一组合，我们仍会占到键、对方也仍可能响应。**未实测**，要覆盖得另开一刀。

### 5.2 两个位置的**像素差**（Phase A 判据②，C6s/C6t/C6u —— 屏幕实测 ＋ 模型对账）

尺子：`PrintWindow` 拿的是**离屏 DIB**（它**不含**整窗常量 alpha），所以透明度必须用**真实桌面合成**来量：
脚本在**窗口出现之前**先抓一张窗口将来位置的桌面（`bg`），然后在**深色主题**下把滑条推到两端各抓一次
（屏幕 ＋ DIB），逐像素对下面这个模型（它由 `lib\ui_lib.fl` 的 `fill_a=200` 与滑条两端 alpha 现算）：

```
out = DIB * a / 255 + bg * (1 - fillA * a / 255^2)
```

| 量 | 实测（最后一轮） |
|---|---|
| 采样点 | **495**（网格 61×53，跳过滑条＋标签那一条带 y∈[170,248)） |

| 两端画面差 中位数 | **92 / 通道**（`scr(max)=84` → `scr(min)=168` 平均亮度） |
| **"没做透明度"的零假设模型**（两次都按默认 236 解释）误差中位数 | **79.96** ⇒ 被同一批像素**否决** |

⇒ 三条判据：`C6s`（模型拟合，中位数 ≤3、p99 ≤6、最大 ≤40）、`C6t`（两端画面差 ≥20）、
