# 流程优化提案（2026-10-28 提出；**#1 / #2 / #5 已于 2026-10-28 01:5x 实施，实测见 §8**）

> 📸 快照：2026-10-28 —— 本文件里的数字是**那一天**的值，不是现行值；现行数字见 `docs\数字台账.md`（取数器 `tools\文档事实.ps1`）。
> 背景：本会话 360 分钟里有 **46% 花在跑门上**（33 次 `gate.ps1` ≈ 165 分钟），另有 **6 次抽块切错白跑**（≈35 分钟）。
> 结构改造本身没问题（`main` 1827→919 行、每步都有绿记录），**问题在流程太贵**：一刀 5~6 分钟，其中 4 分钟是验证。
> 本文只提方案，不实施（2026-10-28：五条里前四条已落地，见 §8；#4 组探针仍待定）。实施时按 §3 的顺序，每步都要能用现有门验证自己（改工具也要可回退）。

## 1. 实测瓶颈（不是体感）

| 环节 | 实测 | 说明 |
|---|---|---|
| 单个探针 | **8.4 ~ 14.3 s** | 各自起一次 app、抢前台、等稳定、注入、抓帧 |
| 全套探针（22 个） | **≈ 4 min** | 21 个行为探针 + 1 个像素快照，串行 |
| 一次 `gate.ps1`（全门） | **5 ~ 6 min** | 编译 15s + 探针 4min + 快照 10s + 性能 80s + 静态 1s |
| 本会话总量 | 33 次门 ≈ **165 min** | 占 360 min 的 46% |
| 失败的抽块 | **6 次** ≈ 35 min | 全是"块内用了 main 的局部量"或"块尾搭在外层包装上" |

**结论**：瓶颈是"**每个探针一份进程 + 每刀必跑全套**"，不是探针本身慢。

## 2. 五条改法

| # | 改法 | 具体做法 | 收益 | 工期 |
|---|---|---|---|---|
| 1 | **性能门降频** | 性能是趋势指标。改成：改动涉及绘制/字体/终端才跑；否则每 5 次提交或交付前跑 | 每刀 −80 s | 10 min |
| 2 | **分层门 `-Quick` / `-Full`** | `-Quick` = 编译 + 像素快照 + **受影响的 3~5 个探针**；`-Full` = 全套（合并/交付前） | 每刀 5min → **1.5min** | 40 min |
| 3 | **抽块静态预检 + 批量** | ① 扫"块内标识符 − (全局 ∪ 形参)"，差集非空**拒绝写盘**；② 一次给 3 个块的计划，全过预检才动手、只编译一次 | 失败重跑 → **≈0** | 1.5 h |
| 4 | **探针组复用进程** | 22 个探针改 4 组（绘制/输入/文件/配置），组内复用一个 app 进程 | 全套 4min → **1.5min** | 2~3 h（风险中） |
| 5 | **门自计时** | 每道门记录耗时，汇总进日志，以后按数据砍 | 长期 | 15 min |

### 2.1 影响面怎么判（#2 的关键）

三选一，从简到繁：

1. **显式声明**：`gate.ps1 -Quick -Touched paint`（人/Agent 指定，最省事，最容易漏）
2. **按符号猜**：`git diff --unified=0` 取改动行，匹配 `paint_*` → 绘制组；`handle_*` / `in.` → 输入组；`std::file_*` / `cfg_*` → 文件组
3. **按探针 tag**：给每个探针加 `# TAG: paint|input|file|cfg` 头，Quick 只跑同 tag

建议先做 1，稳定后再加 2。

## 3. 实施顺序（建议）

```
1（性能降频，10min）→ 2（分层门，40min）→ 3（预检+批量，1.5h）→ 5（计时，15min）→ 4（组探针，2~3h）
```

前四步约 **2.5 小时**，把单刀周期从 5~6 分钟压到 **~1 分钟**，失败率接近 0；第 4 步收益再 30%，但会牺牲定位精度，**留到探针稳定后再做**。

## 4. 改完后的工作流

```powershell
# 一刀
pwsh tools\probes\extract-block.ps1 -Fn handle_xxx -Params "..." -StartPat '...' -EndPat '...' -Call '...'   # 预检不过 = 不写盘
pwsh -NoProfile -File tools\gate.ps1 -Quick -Touched input                                                  # ~40s
git commit -m "..."

# 每 3~5 刀 / 交付前
pwsh -NoProfile -File tools\gate.ps1 -Full
```

## 5. 取舍（必须写清）

- **`-Quick` 有漏检风险**：影响面判错就漏探针。兜底两条：① 合并/交付前必跑 `-Full`；② 像素快照对布局/颜色极敏感（阈值 0.02%），蒙不过去。
- **组探针降低定位精度**：一组红了自己拆。建议只在全绿路径用组模式，红了自动退回单条重跑。
- **预检不是编译器**：标识符扫描只解决"未声明变量"，类型错误仍要靠 `hlc`。所以写盘后编译仍是必跑项（15s，便宜）。

## 6. 验收标准（实施时要满足）

1. 一刀的完整流程（编译 + Quick 门 + 提交）**≤ 90 秒**，实测 5 次取中位数。
2. 连续 10 刀**零编译失败**（预检生效）。
3. `-Full` 跑一次的结果与旧 `gate.ps1` **完全一致**（同样 22 探针、同样阈值）——用同一次改动对比两版输出。
4. 改工具本身的提交必须先过旧门再合并（不许"边改门边放松门"）。

## 7. 不打算做的

- **不做"跳过像素快照"**：它是唯一能抓到"探针全过但像素挪了"的门，本会话已经证明有用（抓过一次 hover 底色、一次快照自身不稳定）。
- **不做"只跑静态门"**：那是自欺——本会话 6 次失败里 4 次编译都没过，静态门看不出来。
- **不改"一个提交一件事"**：提交仍然原子；只是**门**可以按批跑（Quick 每刀、Full 每批）。

**实测（2026-10-28，同一台机、同一二进制 428,032 B）**：

| 模式 | 探针 | 耗时 | 组成 |
|---|---|---|---|
| `-Full` | 22/22 PASS | **430.9s** | 编译 6.6 + 探针 371.6 + 性能 52.1 + 静态 0.1 |
| `-Quick -Touched core`（默认） | 4 | **78.5s** | 编译 6.5 + 探针 71.4（无性能） |
| `-Quick -Touched input` | 5（+snapshot） | **99.0s** | 编译 1.5 + 探针 96.9 |
| `-Quick -Touched paint` | 6（+snapshot） | **163.7s** | 编译 6.5 + 探针 130.7（cjksize 47 / menu 25 / snapshot 17）+ 性能 26.0 |

**验收对照（§6 第 3 条）**：v1 同日基线 = 22/22、15.36 ms/帧、lines 5087 / main 919 / maxFunc 136 / bare 354；
v2 `-Full` = 22/22、15.10 ms/帧、同四个静态数字 ⇒ **同结果**（性能差 0.26ms 属噪声，同一预算 25ms）。

**没达成的**：§6 第 1 条"一刀 ≤90 秒"只对 core（78.5s）和 input（99s，差 9s）成立；**paint 163.7s 不达标**，
原因是三块不可省 —— snapshot 17s（§7 禁跳过）、cjksize 47s（用户报过两次的回归探针）、build 6.5s，
再加性能 26s。再压必须做 #4（组探针复用一个 app 进程，省掉每个探针 5~8s 启动）。

**下一步**：按 §3 顺序继续 #3（抽块静态预检 + 批量，1.5h）→ #4（组探针，2~3h，风险中）。
