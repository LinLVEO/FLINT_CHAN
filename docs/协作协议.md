## 1. 谁是谁（先认清三个角色）

| 角色 | 是谁 | 干什么 | 不干什么 |
|---|---|---|---|
| **所有者 / 拍板方** | `_Lin_chan`（项目所有者） | 定方向与口径、命名、取舍、验收的最后一句、钱 | **不读代码、不写代码**（这是有意设计的，不是缺陷） |
| **实施方** | AI Agent（DeepSeek，在 DSH 引擎里干活） | 写代码、跑门、写文档、记账、留底、复现缺陷 | 不替所有者拍板命名/口径；不悄悄改口径 |
| **协作者** | **你**（外人） | 用、报 bug、提判据、提特性、一起定方向 | —— |

**关键一条**：所有者不做"人 ↔ AI 之间的翻译"。所以**任何需要所有者转达给你、或者需要你转达给所有者的东西，必须写成文件**。
这不是官僚主义，是这个项目唯一可行的通信方式：**聊天会丢，文件不会**。

## 2. 三种通信介质（本项目真正的"聊天记录"）

### ① 工单（`工单-*.md`）—— 一次活的完整形状

一份工单必须自带这六件，缺一件就会被退回来：

1. **目标**（一句话，可判定）
2. **输入 / 上下文**（去哪读、读什么）
3. **允许动什么**（明确写"不许动"的边界：哪些目录、哪些文件、哪些口径）
4. **验收判据**（跑哪条命令、期望什么数字；**先写判据，再写代码**）
5. **产物落点**（文件放哪、日志放哪）
6. **回退点**（动手前的提交号；怎么退）

> 例子：`工单-P1预算仪器接总门.md`（目标 = 把预算纪律变成总门里能跑的一步；判据 = 全量总门 <!--fact:gate-steps-->14<!--/fact--> 步全绿 ＋ 仪器能双向失败）。

### ② 判据（`test\` 的门与探针）—— **对话本身**

**在本项目里，争论不靠嗓门，靠一条能跑的用例。**

- 你说"这里行为不对" → 我们一起把它写成一条用例（`ok` 断退出码 / `wall` 断报错关键词 / `gap` 断"仍然编得过"）
- 机器跑一遍：**红就是红，绿就是绿**。谁的记忆、资历、语气都不算证据。
- 想推翻一条结论？**给一条会红的用例**，我们就改。这就是本项目"提判据 = 一次贡献"的含义。

### ③ 交接块（`PROGRESS.md` 头部）—— 任何人随时接手的锚点

每次收工，实施方把这一块写在文件最上面：**干到哪了 / 当前提交 / 回退点 / 下一刀候选 / 诚实边界（哪些没验、哪些做不到）**。
⇒ 换人、换会话、隔一个月回来，读最上面这一块就能接着干。

## 3. 一次活的标准流程（7 步，顺序不能换）

1. **目标**（所有者给方向；或协作者提需求）
2. **判据先行**：先写"什么算做完"（能跑的命令 + 期望数字）
3. **实现**（小步；一次只动一个变量）
4. **跑门**：改动属于哪一层就跑哪几道门（编译器改动 = 总门 <!--fact:gate-steps-->14<!--/fact--> 步；GUI 改动 = FLGUI 门；语言边界 = 边界探针）
5. **独立复跑验收**：**验收绝不外包** —— 实施者报的数字只当"待核事实"，由另一个人/另一次独立运行复测
6. **交接块**：写清状态、回退点、诚实边界
7. **提交**：提交信息写清"改了什么 + 为什么"；口径变更（重录基线之类）必须写明理由

> 两个我们真踩过的坑，提前说：① **"跑绿了"不等于"对了"** —— 判据本身也会错，见过"门全绿但用户一眼看出界面是空的"；
> ② **同一条命令在不同负载下结论不同**（依赖墙钟的判据会间歇假红），所以"复现"要写清环境。

## 4. 你能怎么参与（按投入从低到高）

| 档 | 做什么 | 门槛 |
|---|---|---|
| **0. 用** | 拿它写个自己的小工具；跑 `test\边界探针.ps1` 验一遍"说明书是真的" | 会一点 C 即可（语法是 C 的子集） |
| **1. 报 bug** | 给**最小复现样本 + 实际输出 + 期望输出**（三样缺一样都会被打回） | 会写一段 `.fl` |
| **2. 提判据**（最受欢迎） | 把一条"必须靠人记住"的规则写成探针用例，交给门去守 | 会读 `.fl` ＋ 会跑 PowerShell |
| **3. 提特性 / 改语言** | 走 `SPEC.md` 设计原则 → 给候选命名 → 所有者拍板 → 立工单 → 判据先行 | 需要一点耐心（语义改动要走全部门） |
| **4. 一起定方向** | 参与"生态位/平台/优先级"这类取舍 | 需要有主张，且愿意把主张写成文档 |

**第一次来最省事的路径**：clone → 按 `README.md` §1 跑通 hello ＋ <!--fact:probe-cases-->44<!--/fact--> 条探针全绿 → 在 `apps\ui_gallery` 或 `apps\student` 上改一行 → 跑对应门 → 提一个 issue 说"我改了这行、门红了、我认为判据太严/不对"。

## 5. 我们对你的保证 / 我们对你的要求

**保证**
- 每个结论都能指到一条**可跑的命令**（不是"应该能行"）
- 每个改动都有**回退点**（提交号 / 留底文件）
- **诚实的边界**：做不到、没验、不知道，一律明写（我们在 `开源前-人类可用性缺口.md` 里连自己哪里难用都列了）
- 你提的判据一旦进了门，**它就会一直被跑**（不会烂在文档里）

**要求**
- 给**可复现的证据**（命令 + 输出），别提"我记得""一般来说"
- 别只看绿灯：**先问这条判据是不是真的能红**（我们把"能双向失败"当判据的合格线）
- 涉及**命名 / 口径 / 是否砍特性** → 找所有者拍板，别和实施方私下拉锯（原则 5：不因"实现麻烦"砍语言能力）
- 一次只改一个变量；改完自己跑一遍门

## 6. 关于"AI 是主力开发"这件事（如实披露）

- **代码主要是 AI 写的**，所有者定方向与验收。这不是秘密，是这个项目的现状与实验之一。
- AI 会犯错，而且犯过的错很具体：改错地方却"看着全绿"、把判据写成自证、复用了长上下文导致偏离。**抓这些错的办法不是"更信任谁"，而是上面那套判据 + 独立复跑 + 交接块。**
- 所以：**你在这里的对手不是 AI，也不是所有者，而是"判据不够"。** 你能带来的最大价值，往往是"我就是按文档做的，但它不对"。
